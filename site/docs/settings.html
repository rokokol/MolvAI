Settings and the Nix-managed mode

Canonical source: crates/molva-core/src/config.rs, nix/module.nix and the settings section of the README

The file

The settings are one TOML file at ~/.config/molva/config.toml, or the matching settings directory on Windows and macOS. It is created at the first start and stays readable by a human

An empty file is valid. Every skipped field comes from the defaults, so the file makes sense as a diff against them. A wrong value fails with the path of the file and the name of the key

molva config path
molva config validate

The defaults below are the ones this site's pages assume. The README lists every field; this table is the small set that changes the behaviour people notice

Hotkeys have their own page: hotkeys and compositors. Journal fields are explained in privacy and journal

The model provider also decides how calls run. A cloud provider may answer up to four calls at once, and a local model takes requests one at a time

Edit and apply

molva config set stt.language auto
molva config edit
molva config reload

The reload passes the new settings to the running daemon. The recognizer and the paste chain are built when the daemon starts, so a changed model, engine or output method needs a restart. molva doctor shows what the daemon actually loaded

The settings page in the GUI

The window edits the same file: the settings page reads the values from it and writes them back. Where Nix generated the file it is hidden by default; programs.molvai.showSettings = true shows it for inspection only, and writing stays refused

  • The recognition provider: a local model or a cloud API. The cloud path is marked as unavailable in this build instead of hidden
  • The model choice with its state: the weights on disk, or a download at the daemon start
  • One field for the speech language, and a list of languages for automatic detection
  • The microphone, from the daemon's list, with a refresh button: the daemon raises the socket only after the weights, and the page says so instead of showing an empty list
  • The key source of each secret: the OS store, an environment variable or plain text in the file with a warning. The model warns separately that text will leave for the cloud
  • Custom styles beside the built-in ones: an identifier, a name, whether the style calls the model, and a system prompt
  • A recorder for every hotkey: press the combination and the page writes it
  • An MCP section: the switch and the ready command for Claude Code, Codex, Cursor, VS Code, Claude Desktop and a terminal

Keys never live in the file

A cloud model key is read from the OS store, from a file with owner-only permissions, or from an environment variable, by llm.api_key_source. The journal key follows the same idea with journal.key_source. Values are written through stdin, so they never enter the shell history

printf '%s' "$KEY" | molva secret set llm
molva secret status

The Nix-managed mode

The Home Manager module does not edit the same file at runtime. It renders the settings and the weights into the Nix store, and a switch is the only thing that changes them

  • home.packages gains molva, and systemd.user.services.molva-daemon runs molva daemon as part of the graphical session
  • The generated settings carry the engine and the model of the catalog entry, the language, stt.auto_pull = false and streaming_inject = false. They also carry the transcribe.cpp binary and backend, and stt.model_path pointing at a store directory of weights
  • xdg.configFile."molva/config.toml" links the generated file into place with force = true
  • With the daemon the module writes ~/.config/autostart/molvai-gui.desktop: the tray icon belongs to the GUI, and the daemon alone does not create one. That is why guiAutostart.enable defaults to daemon.enable
  • The GUI hides its settings page, because every save would be refused. A banner explains that the settings are managed by Nix and names the option to change
  • Under Hyprland with a Lua config the module also writes and includes the binds on each switch. A failure there prints a warning and does not fail the generation
The options of programs.molvai
OptionMeaning
enableInstalls the package and enables everything below
modelThe model name from models.toml, default gigaam-v3-e2e-rnnt-q4_k_m
modelsEvery model to fetch into the store; model must be one of them
modelsDirectoryA directory that already holds the weights, for a machine that gets them another way
language, uiLanguageThe speech language and the interface language
transcribeBackendThe compute backend for transcribe.cpp: auto, cpu, vulkan, cuda
settingsExtra settings merged over the generated ones, in the shape of molva config export
daemon.enableRuns the user service; on by default on Linux
guiPackageThe GUI package the module installs. The default is null, which installs no GUI, and then guiAutostart.command must name a command already on PATH, such as an AppImage
guiAutostart.enableAn autostart entry for the GUI at login. It defaults to daemon.enable, so the entry is written together with the daemon
guiAutostart.commandThe command the entry runs. The default is guiPackage, and molva-gui from PATH when there is no package
hyprland.enableWrites the Hyprland Lua binds and includes the file

A minimal configuration is short. Everything else has a default

programs.molvai = {
  enable = true;
  model = "gigaam-v3-e2e-rnnt-q4_k_m";
  settings.stt.chunk_pause_ms = 400;
};

The rule is the same as for any Nix option: edit the configuration and run your switch. If a value did not take, the banner in the GUI says why
